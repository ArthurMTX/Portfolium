# Contributing to Portfolium

Thank you for your interest in contributing! Portfolium is an open-source, self-hosted portfolio tracker — bug fixes, features, docs, and tests are all welcome.

## Ways to Contribute

| Type | Examples |
|---|---|
| Bug fixes | Crashes, incorrect API responses, UI layout issues |
| Features | New analytics tools, integrations, UX improvements |
| Documentation | Guides, examples, clarifications, screenshots |
| Testing | Backend API tests, frontend unit tests |
| Refactors | Better structure, performance, code cleanup |

If you don't know where to start, check [open issues](https://github.com/ArthurMTX/Portfolium/issues).

## Development Setup

```bash
git clone https://github.com/ArthurMTX/Portfolium.git
cd Portfolium
cp .env.example .env

docker compose -f docker-compose.dev.yml up -d --build
```

| Service | URL |
|---|---|
| Frontend (HMR) | http://localhost:5173 |
| API docs (Swagger) | http://localhost:8000/docs |
| Task monitor (Flower) | http://localhost:5555 |

## Branching & Pull Requests

| Purpose | Pattern |
|---|---|
| Feature | `feat/feature-name` |
| Bug fix | `fix/issue-description` |
| Docs | `docs/update-topic` |
| Refactor | `refactor/module-name` |

Before submitting a PR:

- Keep changes focused and atomic
- Add screenshots for UI changes
- Link related issues (`Fixes #ID`)
- Write meaningful commit messages, e.g.:

```
feat(chart): new sector allocation view
fix(api): incorrect daily P&L rounding
docs(install): expand docker quickstart
```

## Testing

Run the full test suite:

```bash
make test
```

Or target backend/frontend individually:

```bash
make test-backend       # pytest suite
cd web && npm run test  # frontend unit tests
```

See [Testing](testing.md) for what's covered and how CI runs these checks.

## Documentation Checks

Any change to API routes, config settings, models, or user-facing behavior should come with a matching docs update in the same PR. Before submitting:

```bash
make docs-check
```

This regenerates `docs/api/openapi.json` from the running FastAPI schema, checks for placeholder content, verifies every page is tracked in `docs/audit.yml`, and runs `mkdocs build --strict` so broken links and nav entries fail the build instead of shipping silently. See [Documentation Workflow](documentation.md) for the full local preview setup.

## Database Migrations

Schema changes go through Alembic. Generate a migration after changing a model in `api/app/models/`:

```bash
docker compose exec api alembic revision --autogenerate -m "describe the change"
docker compose exec api alembic upgrade head
```

Review the autogenerated migration before committing — autogenerate doesn't always capture everything correctly (renamed columns, some constraint changes).

## Coding Style

| Layer | Conventions |
|---|---|
| Backend | Python 3.11+, FastAPI, SQLAlchemy, Pydantic; formatted with black/ruff |
| Frontend | TypeScript only, React, components kept reusable and accessible |

## Communication

For larger changes, open an issue or discussion first — new API surface or architecture changes, new data providers/integrations, or major UI redesigns benefit from early feedback before you invest time in the implementation.
